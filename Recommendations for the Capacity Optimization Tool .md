Here are some recommendations, we have looked into providing for this tool: 

- When you click on the CVE, you get more information on “Why This Finding Ranks Here”, we want to include more information on why this finding ranks here. For example, we want to include a link where it goes to the actual CVE, EPSS, and KEV, if the links are available. Furthermore, we want more information on “ranked here because”, this is because currently it is just talking about what it sees, but we want a brief overview of what the actual issue is with that CVE. Lastly, we want to provide a recommendation on what they could possibly do and maybe scavenge around to see if there are any open solutions that already readily exist.   
- Currently the max box and font look kind of awkward with our tool, we need to fix that design so it can look proper with the tool that we are making. This can be one of those final adjustments or if it can be done quickly to be fixed.   
- For the dashboard, we want a small overview or like a zoomed in version of the asset map where it shows the crown jewel or a brief overview about it. When you click on it, it leads you to the “Attack surface” section to get a full look at it.   
- Talking about the attack surface, when you click on the asset, I want it to provide more information on what it is like the vendor, a small description, and whatever else may be necessary for a security team to understand.   
- For the theme (specifically the dark theme background), don’t make it like a greenish tone, we want a more dark purple-ish tone. This can also probably be done towards the end.   
- For each aspect of the tool, I want a small i icon (the i icons with a circle around it) and when you hover over it, it gives a small explanation or description of what each part of it represents. For example, dashboard, attack surface, risk engine, plan, team capacity, patching, appsec, change-window. Basically where an explanation can help with better understanding.
- Per-user history (deferred). The first pass of the database + history feature is single-user: one shared history for whoever opens the console, no login. When there's time, extend it so history is separated per user — each saved asset map / plan is tagged with who saved it, and a user only sees (or can filter to) their own runs. This needs at least a lightweight identity (a name or sign-in) and a `user` column on the saved-runs table, which the schema should leave room for.
- History export / import (deferred). The run-history database (`data/scryxen.db`) is intentionally per-machine: it's git-ignored, and the schema is rebuilt automatically from `store.py` on first launch, so any computer that clones the repo gets a fresh, empty history — no `.db` file needs to travel. That's the right default for a single-user local tool. When there's time (e.g. to hand a populated demo to a teammate or back up saved runs), add an explicit export / import: a "download my history" that writes the saved runs to a portable file and a "restore from file" that reads them back. This keeps history movable without committing a binary database to git or standing up a shared/hosted database.
